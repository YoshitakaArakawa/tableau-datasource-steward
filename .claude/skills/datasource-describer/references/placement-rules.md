# 置き場所の判定ルール

## 目次
- 2層と3つの規則

- 判定表
- メタデータに書くこと（M1〜M5）
- コンテキストに書くこと（C1〜C4）
- どこにも書かないこと
- 入出力例

## 2層と3つの規則

| 層 | 答える問い | 置き場 |
|---|---|---|
| メタデータ層 | それは何か | PDS の構造（calc・名前・関係）と説明（列・calc・grain） |
| コンテキスト層 | どう使うか | 組織で共有する決まりは Tableau Knowledge の Business Preference（BP）。データに依らないエージェントの作法はスキル |

1. **判定**: その文は、問う人・問い・場面が変わっても真か。真ならメタデータ、変わりうるならコンテキスト。
2. **依存は一方向**: コンテキストはメタデータを名前で参照してよい。メタデータはコンテキスト（BP 名・グラフ名・スキル名・「〜を問われたら」型の指示）を参照しない。
3. **一か所で定義する**: 同じ語を両方の層で定義しない。

## 置き場所の優先順

**構造 → メタデータ（説明）→ 例 → 文の指示（BP）。** 先に来るものほど古びにくく、コンテキスト層を読まない利用者にも届く。文の指示に回す前に、構造か説明で表せないかを必ず検討する。

例（問いと答えの組）は Tableau Knowledge で持てるかが未確認のため、現時点では使わない。

## 判定表

| 文の種類 | placement | 置き場 |
|---|---|---|
| 合計に意味があるか（単価・率・残高など加算できない measure） | `metadata` | measure の説明（M1） |
| 集計の指示（合計する・平均で見る） | `drop` | どこにも書かない。加算できない性質を含むなら M1 の文に書き直す |
| 1つの PDS 内で式にできる比べ方・指標 | `structure` | 計算フィールド（hoist / calc 注入の候補として報告） |
| 範囲・単位・粒度・性質・値と空の意味・時間的な事実・計算の振る舞い | `metadata` | 列 / calc の説明（M1〜M5） |
| 1行が何か | `metadata` | datasource の説明（grain） |
| 日付・列・データソースの選び分けと既定 | `context` | BP（C1） |
| 問いの言葉の解釈、部門・場面ごとの選択 | `context` | BP（C2） |
| データソースをまたぐ指標・比べ方（1つの PDS の calc にできない） | `context` | BP（C3） |
| 出来事の経緯のうち事実 | `metadata` | 列の説明（M4） |
| 出来事をまたぐ比べ方、データに由来する答え方の決まり | `context` | BP（C3 / C4） |
| 列名の言い換え、自明な値の列挙 | `drop` | どこにも書かない |

1文に複数の種類が混ざるときは、種類ごとに文を分けてから振り分ける。振り分けでは入力に無い事実を足さない。足すなら別の草案として `source: inferred` を付ける（例の出力は振り分けだけを示す）。

## メタデータに書くこと（M1〜M5）

| # | 書くこと | 例 |
|---|---|---|
| M1 | 範囲・単位・粒度・加算できるか。何を含み、何を除き、境界の場合をどう扱うか | 未配達の出荷が1件でもあれば、その注文は完全でない／単価のため合計に意味はない |
| M2 | 性質の違いを、その列自身の言葉で書く | booked / invoiced / cash のうち booked |
| M3 | 自明でない値の意味と、空・null の意味 | 返品を伴わない返金では空 |
| M4 | 値の時間的な性質（事実だけ） | 現在の割当で履歴ではない／2025-01-01 に区分が変わった |
| M5 | 計算の振る舞い。式と1行の粒度から導けるものに限る | 注文単位で判定する／控除は元の請求の日付に入る |

形式:
- 核を先頭150字に入れる（Tableau Agent が索引に入れるのは先頭150字、計4000字まで）。
- 1〜2文。
- 他の列名は、定義の材料としてだけ使う（「X を使え」と選び分けを指示しない）。
- M5 は、似た指標どうしで同じ型の振る舞いを揃えて書く。

## コンテキストに書くこと（C1〜C4）

| # | 書くこと |
|---|---|
| C1 | 日付・列・データソースの選び分けと既定 |
| C2 | 問いの言葉の解釈、部門や場面ごとの選択 |
| C3 | 比べ方・分析の手順。構造で表せるなら構造を先にする |
| C4 | 出来事の経緯（文書として取り込む）と、データに由来する答え方の決まり |

## どこにも書かないこと

- 集計の指示（「合計で集計する」等）: VizQL Data Service のクエリでは集計関数をクライアントが選ぶ。説明では集計を指示せず、加算できない性質だけを M1 として残す。
- 自明な値の列挙: エージェントは値を標本する。取りうる値は、列名から推測できない場合だけ書く。

## 入出力例

**例1: 使い方が混ざった既存の説明**

入力（既存 desc）: 「請求ベースの売上金額。会計年度で見るときはこちらを使い、合計で集計する。」

出力:
- `metadata`: 「請求ベースの売上金額。」
- `context`（C1）: 「会計期間を問われたら、この列を使う」→ `bp_candidates[]`
- `drop`: 「合計で集計する」→ 集計の指示なので消す（金額は加算できるので、M1 として残す性質も無い）

**例2: 出来事を含む説明**

入力: 「販売地域。2025年に地域が再編されたので、年をまたいで比べるときは州コードを使う。」

出力:
- `metadata`（M4）: 「販売地域。2025年に地域が再編された。」
- `context`（C3）: 「2025年をまたいで年を比べるときは、販売地域ではなく州コードで比べる」→ `bp_candidates[]`

**例3: grain に紛れた日付の既定**

入力（datasource.description）: 「注文明細が 1 行。期間は注文日で見る。」

出力:
- `metadata`: 「注文明細が 1 行。」
- `context`（C1）: 「このデータソースの既定の日付は注文日」→ `bp_candidates[]`

## 公式指針との差と代償

- Tableau Agent Best Practices は、説明に「分析での典型的な使い方」も書くよう勧めている。この規範はそれを BP に移すため、公式より厳しい。
- 代償: 説明だけを読むエージェントには、使い方が届かない。構造（calc）を先にするのは、この代償を小さくするため。
